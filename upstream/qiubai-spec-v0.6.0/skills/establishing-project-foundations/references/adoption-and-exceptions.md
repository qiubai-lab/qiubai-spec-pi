# Adoption And Exceptions

## Existing Project

先检查已有入口、结构、命令、context 和已知检查结果；区分已有约定、当前缺口与本次建议。输出最小差异方案，不将“采用基线”理解为全仓库重构。

优先修复真实阻塞：不可运行的验证、无法定位的入口、已影响当前任务的越界依赖。保留正常工作的生态结构、依赖管理和已批准规则。迁移范围超出授权时，只报告额外建议。

渐进采用侧重补齐约定和检查；当请求涉及职责迁移、依赖重整或已有结构替换时，读取 [refactoring-guidance](refactoring-guidance.md) 制定行为基线与迁移验收。已有目标方案直接复用，不重复审计；不将采用规范自动扩大为结构重构。

## Authorization Matrix

| User intent | Allowed scope |
| --- | --- |
| 明确要求按本 skill 创建新项目 | 创建骨架、工程检查、必要工程 context；可调用 initializing-qb-spec 设置根入口 |
| 普通新项目请求，自动选中了本 skill | 设计/实施已授权的工程工作；不据自动选择推断入口修改或长期偏好批准 |
| 明确采用/调整既有项目的某项基线 | 实施并保存该已批准规则；不自动改写 Agent 入口或其他长期规范 |
| 明确请求结构重构 | 在批准范围内诊断、迁移和验证；不隐含产品行为变化或 Agent 入口初始化 |
| 明确要求设置或刷新 qb-spec 入口 | 由 initializing-qb-spec 维护入口，保留无关内容 |
| 仅调研或比较方案 | 返回建议，不创建工程或修改长期 context |
| 普通功能开发、新推断偏好 | 使用已有规则；候选按 maintaining-project-context 的批准流程处理 |

用户在当前会话已经批准的具体范围可以复用，不重复请求确认。关键产品语义、长期 UI 偏好和未批准架构变化不能因创建项目而被当成事实。

## Exceptions

在当前 spec/plan 记录例外的适用范围、理由、替代验证和重新评估条件。没有真实临时期限时不编造到期日；合理的生态差异无需列为技术债。

旧项目已有违规时区分既有问题与新增问题。可以在批准范围内逐步治理，但不能通过关闭全局规则隐藏新增违规。规范与框架冲突时优先保持运行正确，并记录可执行的替代约束。

只有明确批准的长期例外才写入相关 context；当前任务例外保留在 change 中。入口 marker 冲突由初始化 skill 处理，不能自行删除整个入口或覆盖冲突内容。

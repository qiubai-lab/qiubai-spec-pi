# Executable Checks

把适用规则落实到项目原生工具，优先复用已有配置；只有现有工具不能表达重要约束时才写小型检查脚本。具体工具用法以项目锁定版本、现有配置和本地帮助为依据，不假设本参考中的工具已经安装；本地证据不足时记录缺口，不为补全本规范自动引入外部资料。

## Command Capabilities

工程基线记录实际命令、工作目录、前置环境和检查范围；名称由生态决定，不要求统一为 npm scripts。

- 安装：声明运行时范围和依赖；应用按生态锁定可复现依赖，库遵循其发布约定。
- 运行：可重复启动最小入口，说明配置和必要的外部服务；配置示例不含秘密。
- 静态检查：选择适用 formatter、linter、类型或编译检查，避免多工具重复覆盖同一规则。
- 测试：可选择一个模块或场景；持续集成使用非 watch 模式。
- 构建：存在构建或发布产物时验证实际产物；解释不适用项。
- 数据：需要时提供隔离的测试数据和可重建方式；不得把默认初始化/重置指向生产数据。

失败必须沿组合脚本传递为非零退出码，不用忽略错误或绿色占位命令通过 CI。CI 复用相同检查入口；本地快速反馈与完整相关回归分开，不强制固定时间阈值。

## Architecture Enforcement

文件规模按 [code-locality](code-locality.md) 从简单预警开始；实际启用增长治理时才增加比较基准。复用工具或最小统计方法，新增自动检查才验证对应正常、超线及排除场景；预警须有处理结论，不要求小项目先搭治理系统。

存在多个模块时，选择包可见性、受限导入规则或架构测试表达公开接口和允许依赖。可选工具包括 JS/TS 的 ESLint 导入限制或 Nx 边界规则、Python 的 Import Linter、Java 的 ArchUnit；选择与项目兼容的最小机制，不为一种检查迁移构建系统。

配置检查后，在隔离临时副本或可恢复的测试夹具中加入一个代表性违规依赖，确认检查失败且退出码非零；移除后确认正常结构通过。不要把违规文件留在产品源码，不覆盖用户未提交内容。实际规则禁止私有深层导入或循环时，针对这些规则验证，不能只验证任意语法错误。

单模块、静态内容等不适用模块间检查时，记录原因。导入检查不能证明数据所有权或业务职责正确，这些由 `checking-architecture-boundaries` 聚焦审查。

## Walking Skeleton And Feedback

最小用例从真实入口贯通当前必要路径。服务验证一个请求，CLI 验证一次命令执行，库验证一次公开调用，前端验证一个真实页面/状态。存在业务规则时覆盖实际规则；不要编造业务只为满足测试数量。

外部适配器可提供明确标注的本地替代实现用于快速测试；替代实现不能充当真实数据库或第三方集成已经通过的证据。需要集成验证但环境缺失时报告阻塞。

服务端按需提供结构化日志、请求关联信息和明确配置错误；前端提供可复现状态和错误反馈。时间、随机数和网络影响关键规则时提供控制点，避免不稳定测试。涉及敏感信息时日志脱敏。

## Evidence At Completion

将实际命令和结果映射到当前 acceptance。报告安装/启动、最小用例、适用静态/构建检查、边界负例及修复后正例。无适用构建、单模块无边界检查等给理由，不以“未执行”冒充“不适用”。

最终验证遵守现有 `verifying-before-completion` tier 和证据复用规则。后续普通改动仅验证受影响范围，不重新执行整个项目创建验收。
